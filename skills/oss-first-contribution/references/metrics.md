## 1. 三層指標總覽

| 層 | 誰來算 | 計分方式 | 呈現 |
|---|---|---|---|
| 基礎 | 腳本 | 不計分 | 橫向表格，一個專案一列 |
| 客觀 | 腳本 | 0–100 分，依權重加權成「腳本總分」 | 縱向表格＋助手評語 |
| 主觀 | AI 助手（你） | 1–5 分，附證據 | 縱向表格 |

最後由你綜合三層，給一個「助手綜合評分」（1–5）和理由，跟腳本總分分開列。

**跟學生討論時**：從下面的清單挑出來給學生看，每項附「白話意思」那一欄，讓學生選要看哪些、哪些比較重要。不要把整份文件丟給學生。

## 2. 基礎資訊清單

只用來讓學生對專案規模有直覺，不代表好壞：star 多代表很多人用，不代表對新手友善；open issue 多可能是很活躍，也可能是沒人處理。

| 設定名稱 | 顯示 | 白話意思 |
|---|---|---|
| `stars` | ⭐ Star | 有多少人收藏，大概代表知名度 |
| `forks` | Fork | 有多少人複製一份去改 |
| `open_issues` | Open issues | 目前還沒解決的問題數 |
| `open_prs` | Open PRs | 目前等待處理的 PR 數 |
| `contributors` | 貢獻者 | 曾經有 commit 被合併的人數（超大型專案可能拿不到） |
| `language` | 語言 | 主要程式語言 |
| `license` | 授權 | 開源授權條款 |
| `created` | 建立於 | 專案建立日期 |
| `topics` | 主題 | 專案標籤（預設不顯示） |

## 3. 客觀指標清單

每項在 `config.json` 有 `good`（滿分值）、`bad`（0 分值），中間線性給分；`weight` 是權重，設 0 就不看。

### 先知道：「外部」「核心成員」「回應」怎麼判斷

這幾個定義決定了大部分指標，數字怪怪的時候先回來看這裡。

- **核心成員**：GitHub 標成 OWNER、MEMBER、COLLABORATOR 的人，**加上**近 90 天內 commit 數達到 `core_min_commits`（預設 5）的人。後者是為了抓到沒公開組織成員身分的員工：GitHub 會把他們標成一般的 CONTRIBUTOR，如果不排除，員工的 PR 會被當成外部 PR，合併率和合併速度都會被灌高。
- **外部貢獻者**：不是機器人、也不是核心成員的人。
- **機器人**：GitHub 標成 Bot 的帳號、名稱以 `[bot]`、`-bot`、`-ci`、`-commenter` 結尾的帳號，以及內建清單裡的常見機器人（例如 `codecov-commenter`、`github-actions`、`copilot-pull-request-reviewer`）。有漏掉的可以加進 `config.json` 的 `bot_logins`。
- **回應**：只算**核心成員的真人**留言或 review。機器人留言、其他使用者的「+1」、PR 或 issue **被關閉**都不算回應，因為很多專案會用機器人自動關閉不符規定的 PR，算進去會讓專案看起來「秒回」。PR 被合併算回應，因為合併一定是維護者做的。

### 活躍度

| 設定名稱 | 白話意思 | 怎麼算 | 預設權重 |
|---|---|---|---|
| `days_since_last_commit` | 專案還有沒有人在動 | 預設分支最新 commit 距今天數，**分級給分**（見下表） | 10 |
| `commits_in_window` | 最近開發得勤不勤 | 近 30 天的 commit 數（good 20 / bad 1） | 3 |
| `merged_prs_in_window` | PR 有沒有在被處理 | 近 30 天合併的 PR 數，含內部成員（good 10 / bad 0） | 2 |

活躍度的權重刻意壓低（合計 15）：有公司在維護的專案幾乎一定很活躍，但活躍不代表接受外人貢獻。

活躍程度分級（`activity_tiers`，可自訂）：

| 距離上次 commit | 標籤 | 分數 |
|---|---|---|
| ≤ 14 天 | 極度活躍 | 100 |
| ≤ 30 天 | 蠻活躍 | 80 |
| ≤ 90 天 | 普通 | 50 |
| ≤ 180 天 | 偏低 | 20 |
| 更久 | 不活躍 | 0 |

### 對外部貢獻者友善

這組是判斷「新手送 PR 會不會被接受」最直接的指標，權重最高（合計 50）。

| 設定名稱 | 白話意思 | 怎麼算 | 預設權重 |
|---|---|---|---|
| `outside_pr_merge_rate` | 外人送 PR 被接受的機率 | 最近 30 個關閉的外部 PR 中，被合併的比例（good 60% / bad 10%） | 25 |
| `median_days_to_merge` | 外部 PR 送出後大約多久會被合併 | 被合併的外部 PR（至少 3 個）從開啟到合併的中位天數（good 3 / bad 45） | 10 |
| `outside_pr_first_response_days` | 送出 PR 後多久會有維護者真人回覆 | 最近 8 個外部 PR，從送出到第一個核心成員真人留言、review 或合併的中位天數；一直沒有真人回覆的（包含被機器人關掉的），以送出到現在的天數計（good 2 / bad 21） | 15 |

### 維護者回應

| 設定名稱 | 白話意思 | 怎麼算 | 預設權重 |
|---|---|---|---|
| `issue_response_rate` | 開 issue 後有沒有人理 | 抽樣最近 10 個外部使用者開的 issue，有核心成員真人留言的比例（good 90% / bad 30%） | 10 |
| `median_days_first_response` | 多快會有人回 | 上述 issue 第一次被核心成員回覆的中位天數（good 2 / bad 30） | 5 |
| `issue_close_ratio` | 問題有沒有在被消化 | 近 90 天關閉的 issue 數 ÷ 新開的 issue 數（good 0.8 / bad 0.2） | 5 |

### 新手入口

| 設定名稱 | 白話意思 | 怎麼算 | 預設權重 |
|---|---|---|---|
| `open_newcomer_issues` | 現在有沒有現成的新手題目 | 有新手標籤、open、沒人被指派、沒有關聯 PR 的 issue 數（good 5 / bad 0） | 5 |

### 維護者永續性

| 設定名稱 | 白話意思 | 怎麼算 | 預設權重 |
|---|---|---|---|
| `bus_factor` | 少了幾個人專案就會停擺 | 近 90 天的 commit 中，最少幾個人就貢獻了一半（good 3 / bad 1） | 7 |
| `active_maintainers` | 核心成員有幾位 | 依上面「核心成員」的定義計算的人數（good 3 / bad 1） | 3 |

Bus factor 的名稱來自「要有幾個人被公車撞到，專案才會停擺」。bus factor 是 1 代表一個人包辦一半以上的 commit，他一離開，專案就可能停下來。對「送出第一個 PR」來說影響不大，但學生想長期參與時要特別注意。

### 結論門檻、底線與否決條件

- 腳本總分 ≥ 70：適合新手；45–69：可以但要注意；< 45：不建議（`verdict_thresholds`）
- **底線**（`verdict_caps`）：外部 PR 合併率低於 30%，或 issue 回應率低於 50% 時，不管總分多高，結論最多只到「可以，但要注意」。避免一個很活躍、但很少接受或回應外人的專案，靠總分被判成「適合新手」
- 否決條件（`dealbreakers`）：專案已封存，或超過 365 天沒有 commit
- 某項沒有資料時不計分，總分以有資料的權重計算，並顯示資料涵蓋率

### 貢獻門檻

腳本會掃描貢獻說明，標出像「要先有 accepted 標籤的 issue」「沒連到 issue 的 PR 會被自動關閉」「主要給內部使用」這類段落。這不計分，但新手一定要知道：有門檻的專案不是不能貢獻，而是要先照規定走，例如先認領已核可的 issue。

## 4. 主觀指標範例

主觀指標是學生在乎、但腳本算不出來的東西。學生提出想法後，幫他變成「名稱＋怎麼判斷」。學生想不到時，從這裡挑一兩個問他，不要整份列出來。

| 學生可能會說 | 指標 | 怎麼判斷 |
|---|---|---|
| 「想學到東西」 | 學得到東西 | 有沒有用到學生想學的技術（看依賴套件）；review 留言會不會解釋原因 |
| 「不想被兇」 | 社群氛圍 | 讀最近 5–10 個 PR 和 issue 的留言語氣，特別是對新手的回應 |
| 「想練測試」 | 測試文化 | 有沒有 CI、測試資料夾；PR 會不會被要求補測試 |
| 「跟我的興趣有關」 | 興趣相關度 | 對照階段 0 的學生側寫 |
| 「看得懂程式碼」 | 程式碼好不好讀 | 打開幾個核心檔案，看結構、命名、註解 |
| 「怕卡住沒人問」 | 求助管道 | 有沒有 Discord / Slack / Discussions，最近有沒有人在回 |

評分時，每項給 1–5 分，**一定要附證據**：看了哪個 PR、哪段留言、哪個檔案。學生不同意時一起討論。

**五分鐘直覺檢查**：不管學生選了哪些主觀指標，填「助手評語」和「助手綜合評分」前都先看一下這幾點：

- README 有沒有清楚寫怎麼安裝、怎麼跑起來
- 最近幾個被合併的 PR，維護者的留言語氣如何
- 最近幾個外部貢獻者的 PR 是被合併、被耐心指導，還是放著沒人理
- Issue 裡有沒有維護者主動說「歡迎送 PR」
- 有沒有可以問問題的地方

## 5. 學生設定檔

討論完後，把結果寫成這個學生的設定檔，只寫跟預設不同的部分：

```json
{
  "basic": ["stars", "contributors", "language", "license"],
  "metrics": {
    "merged_prs_in_window": {"weight": 0},
    "outside_pr_first_response_days": {"weight": 20},
    "bus_factor": {"weight": 15}
  },
  "activity_tiers": [
    {"max_days": 7,    "label": "極度活躍", "score": 100},
    {"max_days": 30,   "label": "蠻活躍",   "score": 70},
    {"max_days": null, "label": "不活躍",   "score": 0}
  ],
  "subjective": [
    {"name": "學得到東西", "how": "有沒有用到 PyTorch；review 留言會不會解釋原因", "importance": "高"},
    {"name": "社群氛圍", "how": "最近 10 個 PR 的留言對新手友不友善", "importance": "中"}
  ]
}
```

- `basic`、`activity_tiers`、`subjective` 是清單，寫了就整份取代預設
- `metrics` 只要寫要改的項目，其他項目維持預設
- 客觀層只能從第 3 節的清單裡選；想看腳本算不出來的東西，放進主觀層

執行：`python scripts/analyze_repo.py health OWNER/REPO --config student.json`

## 6. 解讀時要注意

- **分數是參考，不是判決。** 小專案的總量指標天生偏低；如果它的回應速度和合併率都很好，對新手可能比熱門大專案更好。這類情況要寫在助手評語裡。
- **數字好到可疑時要查證。** 外部 PR 不到 1 天就有回應或合併時，打開幾個 PR 確認：回應的是不是真人維護者？被合併的外部作者是不是其實是員工？腳本輸出的「用來核對數字的資訊」列了核心成員和被合併的外部作者，可以從這裡開始查。
- **核心成員是推測的。** 只靠 commit 次數判斷：偶爾 commit 的員工可能還是被當成外部；常態貢獻的外部志工也可能被當成核心。數字跟你看到的不符時，以實際讀到的 PR 為準。
- **有些專案在 GitHub 以外的系統合併 PR**，在 GitHub 上會顯示「關閉但未合併」，合併率會被嚴重低估；看到合併率異常低時，打開幾個 PR 確認。
- **比例類指標用樣本數，不用時間窗口。** 30 天內可能只有兩三個 PR，數字會很不穩定，所以合併率、回應速度都抽最近的固定數量（`samples` 可調）。
- **有些專案不用 GitHub Issues**（改用 Jira、郵件列表、Discourse 等），這時 issue 相關指標會是空的。

## 7. 延伸閱讀

- **CHAOSS**（chaoss.community）：Linux Foundation 底下定義開源社群健康度指標的專案。bus factor 在 CHAOSS 叫做 Contributor Absence Factor。想新增指標時，可以先看 CHAOSS 有沒有現成的定義。
