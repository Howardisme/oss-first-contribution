# 各類貢獻的判斷方式與陷阱

## 目錄
1. 新手標籤 issue
2. 補單元測試
3. 翻譯
4. 文件
5. Bug 修正
6. 不建議當第一個貢獻的

---

## 1. 新手標籤 issue（good first issue / help wanted）

**好題目的特徵：** 描述清楚、範圍小、維護者有留下提示（「可以看 `foo.py` 的 `bar()`」）、最近幾個月有人留言或更新。

**要避開的：**
- 已經有人留言「我想做」，而且是最近的留言（用 `claims` 指令檢查；超過一個月沒進度的，可以有禮貌地詢問對方是否還在做）
- 建立超過一年、沒有任何維護者回應（腳本會標 🕸️）
- 留言串裡在爭論該不該做、怎麼做，還沒有結論的

**認領留言範例（英文）：**
> Hi! I'd like to work on this. My plan is to [一句話說明做法]. Could you assign it to me, or let me know if someone else is already on it? This would be my first contribution here.

**之前有人認領、但很久沒下文時（階段 3 標 🟡）：**
> Hi @username, are you still working on this? If not, I'd be happy to pick it up.

等幾天沒有回應，再請維護者指派給你。

## 2. 補單元測試

適合想學測試、又還不熟悉專案架構的學生：讀懂一個函式該怎麼運作、再寫測試驗證，是理解程式碼最好的方法之一。

**步驟：**
1. 先把專案現有的測試全部跑起來，確認環境沒問題
2. 找測試框架的慣例：測試放哪裡、怎麼命名、用 pytest / Jest / Go testing / JUnit 等哪一種、有沒有共用的 fixture
3. 從 `opportunities` 列出的「找不到對應測試」檔案中，挑一個邏輯清楚、依賴少的（純函式最好，避開要連網路、資料庫的）
4. 仿照現有測試的風格寫，涵蓋正常情況、邊界情況、錯誤情況
5. 有覆蓋率工具（coverage、`--coverage`）的話，前後各跑一次，在 PR 裡附上提升了多少

**陷阱：**
- 先確認專案想要這類測試。沒有對應 issue 時，開 issue 或在討論區問「I noticed `foo.py` has no tests. Would a PR adding unit tests be welcome?」
- 腳本是用檔名比對，可能誤判：測試可能放在不同命名的檔案、或是寫在同一個檔案（Rust 的 `mod tests`、Python 的 doctest）
- 寫測試時發現 bug 是好事！但要分開處理：先開 issue 回報 bug，不要在補測試的 PR 裡順手修

## 3. 翻譯

適合語言能力好、程式經驗少的學生，也是很好的入門方式。

**動手前一定要確認：**
1. **專案用什麼方式管理翻譯。** 看 CONTRIBUTING、README、`docs/` 或 i18n 相關 issue。很多專案用 Crowdin、Weblate、Transifex 等平台，翻譯要在平台上做，**直接改檔案送 PR 會被拒絕**（甚至會被下次同步覆蓋）
2. **語系代碼與用字。** 台灣繁體中文通常是 `zh-TW` 或 `zh-Hant`，跟 `zh-CN` / `zh-Hans`（簡體）是不同的語系。不要用簡轉繁工具直接轉換：「軟件→軟體」「默認→預設」「信息→資訊」等用語差異都要處理
3. **專案有沒有術語表（glossary）** 或既有翻譯的風格可參考

**機會在哪：**
- 專案有多語系但缺目標語系（預設 zh-TW）→ 新增語系（先開 issue 詢問，新增語系通常要維護者同意）
- 已有目標語系但落後英文版 → 補上缺漏的字串（比對英文檔多出的 key）
- 文件網站有多語系版本 → 翻譯文件頁面

**品質要求：** 每一句都要人工檢查。機器翻譯（包含 AI）的初稿可以參考，但專案若有 AI 政策要照規定揭露；低品質的機翻 PR 對專案是負擔。

## 4. 文件

**好的文件貢獻：**
- 照著安裝步驟做一遍，修正壞掉或缺漏的步驟（新手的視角最有價值！）
- 補上缺少的範例程式碼
- 補 API 文件中缺少的參數說明、回傳值說明
- 修正過時的內容（跟目前程式碼不符的地方）

**不好的文件貢獻：** 只改一個錯字、改標點、改成自己喜歡的寫法。單一錯字可以修，但建議一次把同一份文件中找到的問題一起修，並在 PR 說明。

## 5. Bug 修正

**適合的 bug：** 可以穩定重現、範圍明確、有標 good first bug 或維護者說明了可能的原因。

**步驟：** 先在自己的環境重現 → 寫一個會失敗的測試（如果專案有測試）→ 修正 → 測試通過 → 在 PR 說明重現步驟和修正方式。

**陷阱：** 無法重現的 bug、涉及多個模組或架構設計的 bug，都不適合當第一個題目。

## 6. 不建議當第一個貢獻的

- **新功能**：除非是很小、有 issue 且維護者明確同意的。新功能常牽涉設計決策，新手容易做了很多最後被拒絕
- **大規模重構、改程式風格**：維護者幾乎不會接受來自新手的這類 PR
- **安全性漏洞**：要走專案的私下回報流程（看 SECURITY.md），不能直接開公開 issue 或 PR
- **只為了刷數量的 PR**：見 SKILL.md 核心原則
